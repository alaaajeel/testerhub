# TesterHub V2 — اقتصاد Hub Coins المقترح

> **مقترح / Demo فقط (لا تطبيق في Firebase الإنتاجية).** القرار النهائي للأرقام والسياسات يحتاج اعتماد مالك المشروع بعد قياس سوء الاستخدام واستهلاك حصة Spark.

## فكرة المنتج
- **100 هب كوين** هدية إنشاء حساب *لمرة واحدة لكل UID* بعد استيفاء شروط التسجيل، وليس لكل تسجيل دخول، ولا هدية متكررة عند تثبيت PWA مجدداً.
- **التطبيق الأول مجاني** دائماً: لا تُخصم أي عملات عند إضافة أول مشروع. سجلات المستخدمين الحاليين يجب أن ترث هذه الأهلية دون حذف بيانات أو تغيير معرّفات.
- **الانضمام للمجتمع العام مجاني**، وكذلك اختبار التطبيقات العامة وطلب الاشتراك في اختبار Google Play لكل تطبيق.
- **مجموعات التبادل بنظام Packs منفصلة كلياً** عن قائمة التطبيقات العامة؛ تكلفة حجز مقعد واحد **100 هب كوين** تُخصم عند تأكيد بيانات التطبيق والانضمام، وليس عند فتح النموذج. رصيد الترحيب 100 يسمح لمستخدم جديد بالانضمام لمجموعته الأولى.
- لكل مقعد تطبيق مستقل: أيقونة، اسم تطبيق، اسم مطور، رابط اختبار Play، وصف، ومهام. لا ينشر في قائمة التطبيقات العامة ولا يستهلك مساحة التطبيق العام الأولى. لا تحصيل عملات مقابل اختبار التطبيقات نفسها.
- **+25 هب كوين** مقابل **تقرير اختبار مفيد ومقبول** فحسب، مرة واحدة لكل مستخدم × تطبيق × يوم بعد مراجعة، وبحد أقصى 5 تقارير مدفوعة بالعملات لكل مستخدم في اليوم (125 عملة/اليوم). المكافآت لا تُصرف مقابل مجرد فتح رابط أو الانضمام أو أي تقييمات مصطنعة.
- **250 هب كوين** لفتح مساحة ثانية لنشر تطبيق آخر في الصفحة الرئيسية، ولا تسمح النسخة المقترحة بأكثر من مساحتين. الأسعار قابلة للتعديل بعد التجربة؛ الإصدار التجريبي يستخدم ثوابت محلية.
- **XP منفصلة** عن Hub Coins: XP للسمعة والترتيب، العملات لإنجازات تتيح ميزات فعلية. لا تحويل إلى نقود أو شراء نقدي أو مقايضة بين الأعضاء الآن.
- لا خصم عملات عند التأخير أو الطرد: الإنذارات وواجبات المجموعة تُدار بالسياسة المنفصلة. لا تربط غرامات بالنظام قبل وجود آلية اعتراض واضحة.

## ما نُفّذ بالمعاينة
- رصيد أولي **100** داخل `localStorage` بالمتصفح نفسه.
- محفظة بتبويب/واجهة مستقلة، مساحات التطبيق، سجل حركات مختصر، عرض سعر التطبيق الثاني، وتفعيل زر فتحه فقط عند كفاية الرصيد.
- إنشاء أول تطبيق عام لا يخصم العملات. إذا امتلأت المساحة المجانية يفتح نموذج المحفظة.
- زر «انضم للمجموعة» يعرض نموذجاً منفصلاً لتطبيق المجموعة؛ لا خصم قبل صحة البيانات والموافقة. عند الحفظ، تُخصم 100 من المحفظة المحلية مرة واحدة ويظهر التطبيق **داخل المجموعة فقط**.
- معاينة Packs V2 تتضمن مجموعتين **توضيحيتين** مفتوحتين: الأولى 15/16 والثانية 3/16. عند الانضمام للأولى تكتمل 16/16، وتختفي من «متاحة للانضمام» وتظهر في «مجموعاتي». تطبيقات الأعضاء الأخرى في المعاينة رموز تجريبية فقط وليست معلومات حقيقية.
- زر **«محاكاة قبول +25»** بعد كتابة تقرير محلي في «اختباراتي»؛ يمنح 25 عملة وهمية مرة واحدة لكل تطبيق/يوم في هذه المعاينة وحدها، لا غير؛ لا يمنح XP حقيقية.
- كل ملفات المعاينة مستقلة تماماً عن Firebase؛ يمكن للمستخدم إعادة ضبط البيانات من «حسابي». هذه **ليست** منظومة أمان للأرصدة الحقيقية.

## هندسة Firestore للإنتاج (عند الموافقة فقط)
```text
wallets/{uid}
  balance: integer
  appSlots: integer             // 1..2
  grantedWelcome: boolean
  updatedAt: timestamp

walletTransactions/{id}         // immutable / Admin-only
  uid: string
  amount: integer
  type: "welcome" | "report_reward" | "extra_app_slot" | "group_join"
  reportId?: string
  dayKey?: "YYYY-MM-DD"
  createdAt: timestamp

exchangeGroups/{groupId}/members/{uid}
  appName: string
  developerName: string
  playUrl: string
  appIconUrl?: string
  description: string
  testingTasks: string
  joinedAt: timestamp
  ...

projects/{projectId}
  ownerUid: string
  ...existing fields...
```

- لا تعطي العملاء صلاحية الكتابة المباشرة إلى `wallets` أو `walletTransactions` أو تعديل قيمة المكافأة من Firestore SDK داخل المتصفح.
- بناء المعاملات المالية المنطقية والأهلية على **معالجة موثوقة**؛ بما أن المشروع على Spark، يمكن النظر في GitHub Actions محمي بـ Firebase Admin SDK وService Account في GitHub Secrets لتسوية تقارير تمت الموافقة عليها. هذه وظيفة إدارية خلفية، وليست أتمتة عميل غير موثوقة. لا تفترض أنها تعمل لحظياً.
- **منح أول مرة** بمعرّف حركة ثابت `welcome:{uid}` وإنشاء wallet في transaction مع شرط عدم وجود idempotency key.
- **تقرير مقبول** بإثبات reviewedAt وapprovedBy وحالة المراجعة، مفتاح حركة ثابت مثل `reward:{reportId}` مع فحص صلاحية التقرير وأهليته وحد 5 تقارير/اليوم، ثم transaction ذرّي عند قبول الحركة.
- **حجز مقعد المجموعة** يجب أن يكون **ذرّياً بخادم موثوق** يفحص أهلية UID، توفر المقعد، انعدام الاشتراك المكرر، الرصيد >=100، ثم يضيف العضوية ويخصم الرصيد ويكتب سجل idempotent. لا تفصل الحسم عن حجز المقعد بخطوتين مستقلتين؛ إذا فشل الحجز لا تُخصم العملات. عند الاستبعاد أو الانسحاب تُطبّق سياسة ردّ رسوم واضحة لم تعتمد بعد. **لا تنفّذ العملية من عميل Firestore مباشرة**.
- **شراء مساحة ثانية** يتم بعملية ذرّية تسحب 250 من الرصيد، تكتب سجل صرف بمعرّف ثابت `slot2:{uid}`، وتزيد `appSlots` إلى 2 إذا الرصيد والأهلية صحيحان.
- راقب إساءة استخدام الحسابات المتكررة، وحسّن الموافقات اليدوية، ولا تحتسب فتح الرابط أو تأكيد ذاتي وحده على أنه اختبار حقيقي.
- لا تغيّر قواعد الإنتاج، أو البيانات الحالية، أو publish workflow قبل اجتياز emulator وCI واختبارات صلاحيات متعددة الحسابات وخطة rollback وقياس Firestore read quota.

## تشغيل مجموعتين أو أكثر بالتوازي
- **سعة المجموعة المعتمدة في تصور V2 = 16 مطوراً** (صاحب التطبيق + 15 مطوراً آخر لاختبار بعضهم). هذا تعديل صريح على فرع التجربة الحالي PR #47 الذي يعتمد 15 عضواً؛ يحتاج مراجعة قواعده واختباراته قبل أي دمج.
- المجموعات ذات الحالة `open` فقط تظهر في «متاحة للانضمام»، و`active` بعد 16/16 تظهر في «مجموعاتي» للأعضاء المخوّلين ولا يمكن الانضمام إليها بعد.
- لزيادة الاستيعاب **دون تفتيت الأعضاء**: اقترح فتح مجموعة ثانية عندما يبلغ عدد أعضاء الأولى 14/16 أو أكثر *ويثبت وجود طلب إضافي* (مثلاً **3 طلبات انضمام منتظرة** أو اعتماد المشرف لإقبال واضح). بعدها تكون المجموعتان مفتوحتين في الوقت نفسه، مع تفضيل ملء الأولى عند عرض الاختيارات.
- تجنّب الاستعلامات والتحديثات المتكررة عن جميع المجموعات. أنشئ المجموعة الجديدة ومعرّفاتها بشكل موثوق ومعاملات للعدد والحالات. تغيير 15→16 يتطلب تعديل `CAPACITY`، القواعد، الفهارس، اختبارات الضغط والعضوية، ومعالجة المجموعات التي سبق أن بدأت بسعة 15 دون إفسادها؛ يفضّل versioned capacity لكل مجموعة بدل تعديل السجلات النشطة.
- التبويب «مجموعاتي» يعرض جميع عضويات المستخدم، بما فيها المجموعات المكتملة والجارية والمغلقة للأرشفة. حالياً معاينة V2 تدعم **عضوية محلية واحدة فقط لكل متصفح** وهي تجربة شكلية لا بيانات حقيقية.

## تصميم الواجهة
- اعتماد الهوية الرسمية: `#092e73`، الأزرق `#1559b7`، الأخضر `#07b978`، الأبيض والدرجات الناعمة؛ خط `IBM Plex Sans Arabic`.
- أيقونات SVG متسقة، بطاقات بزوايا ناعمة، تسلسل بصري واضح وعناصر لمس كبيرة.
- صورة الحساب **قابلة للنقر بالكامل** عبر زر دائري مع أيقونة كاميرا في الإطار (رفع JPG/PNG/WEBP والضغط محلياً).
- لا رابط مجموعة داخل نموذج إضافة التطبيق، فقط رابط اختبار Google Play.
- بطاقات المجموعات تعرض أيقونات التطبيقات بعد الربط الفعلي مع سجلات المجموعة، لا صوراً وهمية تُقدَّم على أنها حقيقية.

## شرط قبل إنتاج V2
إدارة المحفظة، الترحيل، الموافقات، والتزامن بين النسختين لم تُنفذ بعد. تخطيط V2 لا يعني أن Firebase production صار يطبق اقتصاد العملات.
